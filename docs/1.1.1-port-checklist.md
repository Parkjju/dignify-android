# Android port checklist — iOS 1.1.1 / backend 2026-09-02

Written 2026-09-02, following `1.1.0-port-checklist.md`. **Read that one first if the 1.1.0 items
are not all landed** — as of this writing they are: genre reading is gone, `similarTo` is on the
card, the hype-following toggle and seed picker are in My Page, coach marks exist, and
`SoundRoundsScreen` is wired into both the new-user and returning-user paths.

One thing to know before planning: **iOS deleted the sound rounds in 1.1.1.** They were replaced,
not supplemented. Do not port 1.1.1 on top of a rounds screen you intend to keep.

---

## 1. What the backend already serves

Live as of 2026-09-02. No backend work is needed for anything in §2.

| Endpoint | Shape | Notes |
|---|---|---|
| `GET /onboarding/seed-pool` | `{items: [FeedItem]}` | Auth required. **Static, manually curated, no pagination** — the whole pool comes in one response. Seeded and verified 2026-09-02. |
| `GET /picks` · `GET /picks/{id}` | `PickResponse` gains `playCount: Int` | Count of pick-detail opens. |
| `GET /picks/{id}` | side effect | The detail call is what increments `playCount`. List scrolling does not. Nothing to send from the client. |
| `GET /feed/search` | unchanged | The onboarding picker reuses it as-is. |
| `GET /onboarding/candidates` | still served | Kept only for clients still shipping the rounds. **Delete the Android call when §2.1 lands.** |

**Push `type` shipped 2026-09-02** (`d06bd4f`), carrying `curation`, `pick_reaction` or `notice`.
`push_opened{type}` now splits by kind instead of reporting `unknown` for everything.

Android has **no branching at all** — `MainActivity.kt:135` captures the type and does nothing with
it, so even a curation push just opens the app. iOS already had the `curation` branch in a shipped
build, so it recovered on the server deploy alone; Android has to build both branches. That work is
`TODO.md` P6, not part of this port. What is still missing on both platforms is `pickId`, so a
reaction push can only reach "my picks", not the pick itself.

## 2. Work items

Ordered so each compiles and ships on its own. iOS paths are for reading the reasoning; Compose
should do this the Compose way.

### 2.1 Onboarding: sound rounds → pick tracks from a pool

iOS: `Features/Onboarding/SeedPoolPickerView.swift` (new). `SoundRoundsView.swift` was **deleted**.
Android: replaces `feature/onboarding/SoundRoundsScreen.kt`, called from `MainActivity.kt:186`
(new user) and `MainActivity.kt:315` (returning user).

Why it changed: the rounds drew from an 18-track fixed pool and showed six of them. If none of the
six fit, the only way to fix your seeds was Feed → Search → Hype → My Page → Recommend from → Save.
Measured after 1.1.0: 33 users finished the rounds, 10 opened the seed picker, 4 saved. That escape
route was dead, so the picker moved into the onboarding screen itself.

- **One screen. No intro page.** The rounds needed rules explained; "pick some tracks" does not, and
  the first five tracks of a session are the highest-listen stretch there is — delaying them costs
  more than an explainer gains. Title plus one line:
  `Which sound pulls you in?` / `Tap to listen, then pick up to 3.`
- **3-column artwork grid.** This is the one screen that stays a grid — see §3.
- **Artwork tap plays. A separate badge selects.** Both on the same tap and people pick by the name
  they recognise instead of the sound, which is the exact failure the rounds existed to avoid. The
  badge is 24dp with a **44dp touch target**.
- Show the play glyph on unplayed cells too, dimmed. If it only appears while playing, nobody
  discovers that the cells are playable.
- **Max 3** — must equal `SeedTracksUpdateRequest @Size(max)` and `MoodRecommender.SEEDS` server-side
  and the seed picker's limit. Over the limit, show a line at the bottom; do not silently ignore.
- Search reuses `GET /feed/search`. **Do not paginate the results** — three seeds, one page is enough.
- **Await the hypes, then report completion.** Fire-and-forget lets the first feed request beat the
  hypes and the user's first feed is unsorted. iOS awaits them behind the button spinner.
- `Skip` top-right finishes with 0. The bottom button needs at least one pick.
- **Keep the `didSoundRounds` preference key** (`MainActivity.kt:206 KEY_DID_ROUNDS`). Renaming it
  re-shows onboarding to every user who already went through it.
- Delete `Api.OnboardingCandidates` and the `/onboarding/candidates` call once both sites are moved.

### 2.2 Pick compose: artwork grid → date-grouped list with playback

iOS: `Features/Picks/PickComposeView.swift`, cell extracted to `Features/Picks/PickTrackRow.swift`.
Android: `feature/picks/PickComposeSheet.kt`.

53 users opened the compose screen and 45 left with nothing; 32 of them never came back for a second
try. The grid is fast for finding a track you already know, but a hype list is mostly tracks you do
not remember. Dates restore the context ("what was I digging that day") and playback finishes the job.

- ⚠️ **`PickComposeSheet.kt:98` currently argues *for* the grid** ("3열 그리드인 건 아트워크로 고르는
  화면이라서다"). That reasoning is now reversed for this screen. Rewrite the comment, or the next
  reader restores the grid and thinks they are fixing a regression.
- `Candidate` gains `previewUrl` and `hypedAt`. Both already arrive on `Api.HypeItem`; search results
  give `previewUrl` but no `hypedAt`, so it is nullable and those tracks group separately.
- ⚠️ **Keep comparing by `trackId` only.** Android already does this
  (`PickComposeSheet.kt:291` `indexOfFirst { it.trackId == track.trackId }`). iOS compared whole
  values, and once `hypedAt` was added the same track from search and from the hype list stopped
  matching: the cell rendered unselected and a second tap **added a duplicate** instead of clearing
  it. Android does not have this bug; do not introduce it by switching to `Candidate` equality.
- Tracks picked from search have no `hypedAt` and belong in a section above the date groups. Without
  it they vanish from the list the moment the query is cleared.
- **Reuse `HypeGrouping`.** Its `dayGroups` is typed to `Api.HypeItem`; iOS pulled the core out as a
  generic `byDay(items, date:)` and had `dayGroups` call it. Do the same rather than writing a second
  grouper — the two lists must never split by different day rules.
- Pagination still triggers on the **last row**, not the last date group. A page that is all one day
  leaves the group key unchanged and the trigger never fires again (iOS 1.0.9 bug, already noted in
  `HypeGrouping.kt`).
- Playing from the hyped position is **not possible** — the server does not store an offset.
  Preview plays from the start.

### 2.3 Play count on the pick card

- `Api.Pick` gains `playCount: Int? = null` (nullable for the same reason `isOfficial` is).
- Render next to the track count in the same row, display-only styling — in that row, only things
  with a pill background are buttons.
- **Hide it below 5.** "Played 3 times" is a worse signal than nothing; it tells the creator their
  pick was not read.
- ko string is `재생 %d회`, not `%d번 재생`. Opening a pick starts playback immediately, so it is a
  play count, not a view count — but the phrasing should read as a stat label.

### 2.4 Wording: crate → hypes

`R.string.your_crate` (`PickComposeSheet.kt:195`, `:219`, `DiggingProfileScreen.kt:629`) and
`R.string.pick_crate_empty` (`PickComposeSheet.kt:260`).

- en `Your crate` → `Your hypes`; `Nothing in your crate yet — …` → `No hyped tracks yet — search for
  tracks to add.`
- **ko changes too**: `담은 곡` → `하입한 곡`. Korean already says 하입 everywhere else, so changing
  only English leaves the same two-names problem in the language most users read.
- "crate" is not a typo — it is where the app's name comes from (crate digging). It goes because it
  appears in three places and is never learned, while 하입 is everywhere.

### 2.5 Analytics

**Event names and property keys must be byte-identical to iOS** — one PostHog project, and a single
differing character halves the funnel. New in 1.1.1:

| Event | Properties |
|---|---|
| `onboarding_seed_shown` | `pool_size`, `is_update` |
| `onboarding_seed_previewed` | `track_id`, `from` (`pool`\|`search`) |
| `onboarding_seed_searched` | `query` |
| `onboarding_seed_selected` | `track_id`, `from`, `selected_count` |
| `onboarding_seed_done` | `count` |
| `pick_track_previewed` | `from` (`crate`\|`search`) |
| `pick_track_selected` | `from`, `selected_count` |
| `pick_title_step` | `track_count` |
| `pick_submit_failed` | `reason` (`server`\|`network`), `track_count` |

Retired with the rounds: `onboarding_sound_picked`, `onboarding_sound_skipped`,
`onboarding_sound_completed`. Leave the old data alone; just stop sending them.

Two rules that carry over: fire **previewed** only when a new track starts (a re-tap is a pause, and
counting it inflates the number that decides whether playback helped), and fire **selected** on add
only, not on remove.

## 3. Decisions already made — do not relitigate

- **The onboarding picker is a grid; the pick composer is a list.** They answer different questions.
  Onboarding scans tracks you do not know, where artwork is the fastest thing to scan and there is no
  date axis at all. Pick compose recalls tracks you already met, where names and dates carry the
  memory. The shared piece is the **playable selection cell**, not the layout.
- **The seed pool is static and hand-curated.** Not a live ranking. Refreshing it is an ops task
  (`ops/onboarding-seed-pool.sql`), same as the curation sets.
- **Picked tracks are hyped through `POST /tracks/{id}/hype`.** The seed derivation path did not
  change; onboarding just produces hypes like everything else.
- **Skip stays.** A user whose taste is not in the pool must be able to leave; the feed cold-starts
  them.
- **Play count is shown to everyone, not only the creator.** It reads as reach for the creator and
  as social proof for everyone else, and gating it by owner costs a branch for nothing.

## 4. Versioning — already corrected 2026-09-02

Recorded here because the numbers do not line up with iOS and the next person will wonder why.

The hype-following feed shipped to Play as **`versionCode 8` / `versionName 1.0.1`** — `35dc1ef`
raised the code from 5 to 7 while rolling the name back from `1.0.1` to `1.0.0`, and `dec8b73`
landed on 8 / `1.0.1`. `Changelog.kt` had no entry for either, and `shouldShow` returns false for a
version with no notes, so **nobody who took that update was told the feed had changed.**

Fixed on 2026-09-02: `versionCode 9` / `versionName "1.1.0"`, with a five-line `1.1.0` entry naming
what already shipped (hype-following feed, genres gone, seed picker, random toggle, "because you
hyped" badge). No code changed — this release exists to give shipped work its notes.

**Do not add 1.1.1 notes until the port in §2 is done.** The Changelog comment says the same thing.
Android and iOS version names are allowed to diverge; the backend targets pushes by `versionCode`,
which is its own counter either way.

## 5. Verification

- `gcloud logging read 'textPayload:"[feed]"'` → `source=mood` means personalisation ran. If Android
  traffic only ever shows `cold` right after onboarding, the hypes are not landing before the first
  feed request (§2.1, the await).
- Check `onboarding_seed_selected` for the `from` split. **A high `search` share is the finding**: it
  means the fixed pool does not cover real taste and the pool needs re-picking.
- `pick_track_selected` versus `pick_title_step` versus `pick_created` finally splits the compose-screen
  drop-off into "never picked a track" and "picked but never posted". Before 1.1.1 there was nothing
  between opening the screen and posting.
- The User-Agent still carries `dignify/<versionCode>`; the backend reads it for version-targeted
  pushes. Do not replace it.
