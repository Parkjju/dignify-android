# Android port checklist — iOS 1.1.0 / backend 2026-08-25

Written 2026-08-25 for whoever (or whatever) picks up the Android port. Android currently sits at
`versionName 1.0.1` / `versionCode 5`, which is feature parity with **iOS 1.0.x**. iOS has since
shipped 1.1.0 and the backend behind it is already live, so Android is now behind on the single
biggest change the product has made: **the feed no longer reads genres, it follows what you hype.**

Read the "Decisions already made" section before designing anything. Most of the open questions in
this list were argued out on iOS and settled with measurements; re-deciding them costs a day and
lands somewhere worse.

---

## 1. What the backend already serves

All of this is live. No backend work is needed for the Android port.

| Endpoint | Shape | Notes |
|---|---|---|
| `GET /feed` | `{items, nextCursor, hasMore, genreExhausted}` | 30 items per page now (was 10). `genreExhausted` is always `false` — kept only so old clients don't break. |
| `FeedItem` | `…, isHyped, similarTo` | `similarTo` is `{trackId, trackName, artistName}` or `null`. It names the hyped track that made this card surface. Only mood-ordered cards have it; cold-start, random, search and curation cards do not. |
| `GET /users/me` | `…, diggingMode: Boolean` | |
| `PATCH /users/me/digging-mode` | body `{"enabled": true\|false}` → 204 | |
| `PUT /users/me/seeds` | body `{"trackIds": [long]}` → 204 | Max 3. Empty array clears the pins. Track ids the user has not hyped are silently ignored. |
| `GET /users/me/hypes` | `HypeItem` gains `isSeed: Boolean` | Used to render the current pin state in the picker. |
| `GET /onboarding/candidates` | `{rounds: [{axis, highTrackId, items: [FeedItem]}]}` | Requires auth. Three rounds, two items each, order shuffled. `highTrackId` says which of the two is the HIGH end of that axis. Currently seeded with six fixed K-Pop tracks, so **every user gets the same three rounds** — that is intentional. |
| `PUT /users/me/genres` | still accepts, still writes | The feed no longer reads `user_genres`. The endpoint stays so old clients don't error. **Do not call it from new Android code.** |

Unknown fields are additive only; nothing was removed from any response.

## 2. Work items

Ordered so each one compiles and is shippable on its own. iOS file references are for reading the
reasoning, not for transliterating — Compose should do this the Compose way.

### 2.1 Stop reading genres (blocking, do first)

The server ignores `user_genres` entirely. Android still has genre selection in onboarding
(`OnboardingStep.GENRES` → `GenreSelectionScreen`) and in My Page (`MyRoute.GENRES`), so an Android
user today picks genres, sees them saved, and gets a feed that ignores them.

- Remove the genre step from onboarding and the genre row from My Page.
- Keep `GenreSelectionScreen.kt` on disk if you like, but unwire it. The table and rows still exist
  server-side; only the code stopped reading them.
- `genreExhausted` handling and any "more beyond your genres" toast should go with it.
- The genre pill on the feed card (`GenrePill`, `FeedScreen.kt:896`) is replaced in 2.3 below.

### 2.2 Sound rounds replace the taste quiz

iOS: `Features/Onboarding/SoundRoundsView.swift`, wired in `App/MainTabView.swift`.
Android: replaces `QuizIntroScreen` + `TasteQuizScreen` (`TasteQuiz.kt`, `PredictedType.kt` scoring
stays — it feeds the profile badge, not the feed).

Three rounds, two audio clips each, "pick the one you'd rather keep listening to". Picking hypes
that track, which makes it a feed seed immediately. Rules learned on iOS:

- **Do not label which card is which end before the pick.** Show the axis label only after they
  choose, otherwise people pick the label instead of the sound.
- **Fetch the rounds before presenting the screen** and pass them in. Presenting on a boolean and
  loading inside gave an empty screen on iOS (the content lambda captured the pre-load value).
- **If `rounds` is empty, present nothing and do not burn the "seen" flag.** The candidate table can
  be unseeded; a user who hits that must still get the rounds later.
- Run it once for updating users too, not just new installs — see 2.7.

### 2.3 "Because you hyped X" on the feed card

`FeedItem.similarTo` replaces the genre pill in the same slot. One slot, not two: a badge that
appears on some cards and not others reads as those cards being special. Fall back to the genre name
when `similarTo` is null.

### 2.4 Hype-following toggle

- `Session` gets a `diggingMode` flag, loaded from `GET /users/me`, written by
  `PATCH /users/me/digging-mode` optimistically with rollback on failure.
- Two controls share it: a switch in My Page and a button in the feed's top bar.
- Changing it must bump `feedReloadTick` so the feed drops its cursor and refetches. Keeping the
  cursor serves pages built from the old ordering and looks like the switch did nothing.
- The feed shows a chip saying which mode is on — **including when it is on.** "Following your
  hypes" / "Random". If it only appeared when off, the on state has no name and nobody can tell
  what the button does without pressing it.

### 2.5 Seed picker ("Recommend from")

iOS: `Features/MyPage/SeedPickerView.swift` + selection mode in `HypeCollection.swift`.
Android: a new screen reusing `HypeCollection.kt` in a selection mode.

- Pin up to 3 hyped tracks; those become the only seeds. Pin none and the server falls back to the
  three most recent hypes.
- Load current state from `isSeed` on `GET /users/me/hypes`. Pins can live beyond the first page —
  merge them in as pages load, but **never re-add a pin the user just cleared on screen.**
- Over the limit, do nothing. Silently evicting the oldest pick means the user cannot see what left.
- Saving bumps `feedReloadTick` (same reason as 2.4).
- If hype-following is off, say so on this screen. Otherwise saving pins and seeing no change reads
  as a bug.

### 2.6 Coach marks

iOS: `Features/Onboarding/CoachMarks.swift`. Android has none (`PickListScreen.kt:102` notes this).

Four screens want them: feed (what the hype button does, what the mode chip means), picks tab,
My Page (the two settings that change the feed), and the seed picker.

The seed picker one is the interesting case: it walks the user into actually pinning a track rather
than just describing it. **Anchors must be measured, not hardcoded** — every user's crate has a
different number of tracks and date groups, so a fixed coordinate is wrong for everyone. In Compose
use `onGloballyPositioned` to collect bounds, and skip the cutout when the target is outside the
viewport (scrolled away) rather than punching a hole nobody can see.

### 2.7 Update flow

`MainActivity` needs the returning-user branch iOS has:

1. Signed in, did not just onboard, has not done the rounds → run the rounds once.
2. When that closes, show What's New for the new version (`Changelog.kt`).

Two things iOS got wrong first and fixed:

- **Do not gate the rounds on hype count.** iOS skipped them for anyone with 3+ hypes, reasoning
  that three round picks would take all three seed slots. That was dropped once the seed picker
  shipped: a user whose seeds get taken can now re-pin, and skipping the rounds means the users with
  the most history never see what changed.
- **Do not let the rounds swallow What's New.** Chain them on dismiss. Writing the "last seen
  version" outside the branch means the notes are skipped forever for exactly the users who need
  them.

### 2.8 List editing and small fixes

- Edit buttons on the crate and artist requests (long-press is invisible to first-time users). For
  picks, use the `···` sheet instead — it already carries rename and delete.
- Removing from the crate asks for confirmation and animates the removal. In edit mode the whole
  cell is a target, so a finger brushing past while scrolling drops a track with nothing on screen
  to show it.
- Deleting a hype must refresh the digging profile stats — they are derived from hype counts.
  **Signal it after the server call, not on the optimistic edit**, or the refetch races the delete
  and returns the old numbers.

### 2.9 Analytics (done 2026-08-25)

Everything in this port that the user can operate is instrumented, with **event names and property
keys identical to iOS** — both apps report into one PostHog project, so a single differing character
splits the funnel in half. The event table lives in `digging/09_analytics_queries.md` §A-18.

`digging_mode_changed{enabled,source}` · `seed_picker_opened{pinned}` · `seed_saved{count}` ·
`coach_shown{screen}` / `coach_finished{screen,last_step}` · `hype_removed{via}` ·
`pick_renamed{cleared}`.

Two rules that are easy to get wrong:

- **Fire after the server call succeeds, not on the optimistic edit.** A toggle that failed and
  rolled back would otherwise count as "turned it off".
- **One capture in the shared function, not one per call site.** The mode toggle has two entry
  points, rename has two screens, and crate removal has two routes; each is a single capture with a
  `source`/`via` property.

## 3. Decisions already made — do not relitigate

- **The catalog is not filtered by genre for anyone.** 2026-08-25 the backend also re-enabled 35,753
  tracks that were switched off by an old genre sweep (active: 28,874 → 64,627).
- **Every user sees the same three onboarding rounds.** Six fixed tracks, chosen by ear for being
  recognisable in Korea. Only left/right order varies. Do not "improve" this by randomising.
- **No forced update.** Considered and dropped: it cannot help the clients already in the field, and
  it risks review rejection.
- **No compatibility shim for old clients.** Old versions get the whole catalog; that is the point of
  the release.
- **Page size is 30.** Do not prefetch a whole page of artwork — window it around the current card.

## 4. Verification

- The one server-side signal that personalisation is actually running:
  `gcloud logging read 'textPayload:"[feed]"'` → `source=mood` (personalised), `cold` (no hypes yet),
  `random` (fallback), `off` (hype-following disabled). If Android traffic only ever produces
  `random`, something is silently falling back.
- The backend serves Korean names via `Accept-Language`; make sure the header still goes out.
- The server reads the app build from the default User-Agent (`dignify/<versionCode>`) and stores it
  with device tokens for version-targeted pushes. **Do not replace the User-Agent** — it breaks that
  quietly.
