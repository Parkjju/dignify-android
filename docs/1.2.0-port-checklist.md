# Android port checklist — iOS 1.2.0

Written 2026-09-03, following `1.1.1-port-checklist.md`. That one is fully landed (Android shipped
it as `1.1.2` / `versionCode 11`), so this checklist starts from there.

**Status (2026-09-03): §2 is fully landed** — shipped as `versionName 1.2.0` / `versionCode 12`.
Two deviations from what is written below, both explained in the repo `TODO.md`:
`track_playback_started` was not created (Android never had that event), and "does a next track exist"
is read at fire time rather than snapshotted (pagination appends with no recomposition to see it).
**§4 is partly run** on a moto g 2025 (Android 16): items 1, 2, 5 and 6 pass; 3, 4 and 7 are still open.
One finding worth carrying to the next port: **a media notification action icon cannot carry a colour** —
the system tints it monochrome, verified on device. The hype button therefore signals state by shape
(shovel / check), not by the brand colour the design system uses everywhere else.

iOS 1.2.0 is one feature: **digging keeps going with the screen off.** Background playback, lock
screen controls, auto-advance in the background, and hype from the lock screen.

**No backend work.** Nothing here touches an endpoint. The only server-visible change is two new
properties on events that already exist.

---

## 1. Read this before planning: the platforms are not shaped the same here

This is the one port so far where a direct translation is wrong. iOS and Android solve background
audio with different machinery, and three of the five iOS work items collapse into one on Android.

| iOS | Android |
|---|---|
| `UIBackgroundModes: audio` in Info.plist. Nothing else — the process just keeps running while audio plays. | **A foreground service is mandatory.** `MediaSessionService` + a permanent notification. Without it the process is killed. |
| `MPRemoteCommandCenter` registration for play/pause/next/prev. Lock screen, Control Center, earbuds, car and Watch all attach to it. | `MediaSession` gives the same surfaces (notification, lock screen, Bluetooth/AVRCP, Wear, Android Auto) from the `Player` commands. |
| `MPNowPlayingInfoCenter` dictionary, set by hand. | The media notification is built from the `MediaSession`. Mostly automatic. |
| **A Live Activity** — a separate widget extension target, a shared `ActivityAttributes` type, and a `LiveActivityIntent` — existing only to hold a hype button that Now Playing has no room for. | **No equivalent, and none needed.** The media notification is that surface. Hype is a `CommandButton` in the session's custom layout. |

So the Live Activity is not a port item. **Do not build a widget or a second process.** The thing it
exists to provide on iOS — a hype button on the lock screen — is a custom action on the
`MediaSession` here, and it lands in the same notification as the transport controls rather than
stacking a second card underneath them.

The trade is that Android needs a service iOS did not, and that service is most of the work.

## 2. Work items

Ordered so each compiles and ships on its own.

### 2.1 Foreground service and the manifest

New dependency: `androidx.media3:media3-session` (the version catalog already pins `media3 = 1.5.1`;
`media3-exoplayer` is in `app/build.gradle.kts:105`).

`AndroidManifest.xml` needs all three of these. The manifest has none of them today:

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />
...
<service
    android:name=".feature.feed.DiggingPlaybackService"
    android:foregroundServiceType="mediaPlayback"
    android:exported="true">
    <intent-filter>
        <action android:name="androidx.media3.session.MediaSessionService" />
    </intent-filter>
</service>
```

⚠️ **`FOREGROUND_SERVICE_MEDIA_PLAYBACK` is required from Android 14 (API 34).** Omitting it does
not warn — the service throws `SecurityException` at startup on 14+ and playback dies where it
worked on 13. Test on a 14+ device, not only on whatever is plugged in.

⚠️ **`android:exported="true"` on the service is not a mistake.** Media3 requires it so the system
media controls, Bluetooth and Wear can bind. The lint warning is expected.

### 2.2 Stop pausing on background

`feature/feed/FeedScreen.kt:296` is the only thing stopping background playback:

```kotlin
Lifecycle.Event.ON_PAUSE -> audio.pauseCurrent()
Lifecycle.Event.ON_RESUME -> audio.resumeCurrent()
```

Delete both lines. iOS deleted the equivalent `scenePhase` handler.

**But do not simply delete and move on.** iOS moved the decision into the controller, because the
one-line preview player on My Page (`HypeCollection.kt:161`) and the pick compose sheet
(`PickComposeSheet.kt:159`) must still stop when the app leaves the screen — only the feed keeps
going. iOS added an `isFeedSession` flag set by `updateWindow` and cleared by `togglePreview`, and
subscribes to the background transition in the controller rather than the view. Do the same:
`ProcessLifecycleOwner` in `FeedAudioController`, not a per-screen observer.

Reason iOS gives, which applies here too: screen-level lifecycle is not trustworthy for deciding
this, because the answer depends on which playback session is live, not which composable is
resumed.

### 2.3 MediaSession: transport controls and the hype action

`FeedAudioController.kt` already holds a sliding window of three `ExoPlayer` instances, so there is
no single `Player` to hand a session. Two options, in order of laziness:

1. Give the `MediaSession` the **current** player and re-point it on every `setCurrent`
   (`FeedAudioController.kt:150`). Smallest change.
2. Wrap the window in a `ForwardingPlayer` that always delegates to the current player. Cleaner if
   option 1 starts leaking window mechanics into the session.

Start with 1.

`SessionCommand` for hype goes in the custom layout. The callback routes to
`FeedViewModel.toggleHype` (`FeedViewModel.kt:291`) — the same function the on-screen button calls.
iOS was strict about this: the optimistic update, the rollback and the `track_hyped` event must not
fork. `setHypeLocally` (`FeedViewModel.kt:332`) is where the state lives, so the notification's
button state has to be refreshed from there too, the way iOS added `syncHype`.

Next/previous need the feed index, which lives in the view model, not the controller — same split as
iOS. iOS solved it with an `onRemoteSeek` callback and made the handler call `updateWindow`,
`prefetch` and `logTrackViewed` **explicitly** rather than relying on a state observer, because in
the background SwiftUI stops re-evaluating. **Compose has the same hazard for a different reason:**
with the app backgrounded there is no recomposition to hang side effects off, so anything in a
`LaunchedEffect(currentIndex)` will not run. Move those calls into the handler.

Pagination has the same problem — `loadMoreIfNeeded` must be called from the handler, not from a
scroll effect.

### 2.4 Auto-advance in the background

`FeedAudioController.kt:82` and `:120` set `repeatMode = Player.REPEAT_MODE_ONE` — the 30-second
preview loops forever. iOS keeps that in the foreground (you can swipe at any time, so looping while
you decide is right) and **advances in the background** (there is no swipe out there, so looping
means the same 30 seconds repeating in a pocket).

Android has no notification for "a repeating item looped". Switch to
`Player.REPEAT_MODE_OFF` plus `Player.Listener.onPlaybackStateChanged(STATE_ENDED)`, and decide
there: in the foreground seek to 0 and play, in the background advance. iOS put that decision in one
function, `handleTrackEnd(id:)`, with a unit test — mirror it into `Playback.kt`, which is already
the home for controller logic that can be tested without a player.

At the end of the feed, advancing fails and it falls back to looping until pagination appends more.

### 2.5 The `background` property on three events

`track_viewed`, `track_dwell` and `track_playback_started` each gain `background: Boolean`. Names and
semantics must match iOS or the two platforms cannot be read together.

⚠️ **`track_dwell` is not the same rule as the other two.** Do not read the flag at send time. A user
who listens for ten minutes in a pocket and then swipes after returning sends the event from the
foreground, and reading the flag at that moment records ten minutes of pocket time as foreground
dwell. The dwell distribution is what decides where `LISTEN_THRESHOLD_SEC` should move, and its
measured median is 2.0 seconds — one 600-second sample distorts it.

iOS marks the flag **on entering the background** and clears it at flush. `DwellTracker`
(`Playback.kt`) is the right place: add a `hadBackground` flag set from the same
`ProcessLifecycleOwner` observer as 2.2, returned by `flush()` and reset there.

`track_listened` needs no flag. It fires once per track at 5 seconds and 30 seconds heard in a
pocket is still 30 seconds heard.

**Known gap, same on both platforms:** auto-advance and a manual lock screen skip both produce
`track_viewed{background: true}` and cannot be told apart. That answers "is background used" but not
"is the user actively skipping". iOS decided not to add a second property until there is a reason to
ask. Do not add one here unilaterally.

## 3. Versioning

Android is on `1.1.2` / `versionCode 11`; iOS shipped this as `1.2.0`. The names are already out of
step and that is fine (§4 of the 1.1.1 checklist) — the backend only reads `versionCode`.

**Next upload is `versionCode 12`.** 11 is spent.

Whatever `versionName` you pick, **the in-app changelog entry must use that exact string.**
`Changelog.shouldShow` filters out versions with no notes, so a mismatch silently hides the whole
What's New sheet. iOS release note text, for translation:

```
Tracks keep playing when you leave the app or turn the screen off.
Skip tracks from the lock screen, your earbuds, or your car.
With the screen off, each track rolls into the next one on its own.
Hype a track right from the lock screen.
```

The third line describes background-only behaviour. If 2.4 does not ship, drop that line rather than
reword it.

## 4. What to check on a real device

The emulator hides most of this — the foreground service, the notification and Bluetooth all behave
differently there.

1. Play the feed, press home, then lock. Audio continues and a media notification is present.
2. Skip from the notification, from the lock screen, and from a Bluetooth headset.
3. Preview a track on My Page, press home — **it must stop.** This is the `isFeedSession` split.
4. Leave it locked for two minutes — tracks advance on their own and the notification follows.
5. Hype from the notification, then open the app: the track is hyped there too.
6. **Android 14+ specifically** — 2.1 fails only on 14+, and it fails at service start, not at build.
7. Swipe the notification away and confirm playback stops cleanly rather than orphaning the service.
